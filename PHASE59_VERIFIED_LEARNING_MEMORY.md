## Why Phase 59 Exists

Phase 56 documented the gap in its own words: *"Not implemented — the evidence
does not exist… Building the trail would have meant inventing order from
totals."* Phase 41's counters are cumulative and carry no chronology. Phase 59
creates that chronology, from now on, as real append-only events.

## Existing Evidence Before Phase 59

- **Cumulative**: `solvedCount` / `struggledCount` / `againCount` on
  `users/{uid}/studyItems/{questionId}` — authoritative, monotonic, complete
  only when their sum equals `attemptCount`.
- **Ordered**: none. `lastOutcome` / `lastReviewedAt` are current state, not a
  sequence. The teacher's `recentOutcomes` sample is one outcome per *distinct*
  question, not a within-question timeline.
- **Reconstruction possible: NO.** Confirmed by audit (§7) — no attempt
  documents, no session records, no per-outcome analytics collection exists.

## Chosen Event Architecture

`users/{uid}/studyEvents/{eventId}`, written **inside the existing
`recordStudyOutcome` transaction**.

That callable is already server-authoritative (uid from `request.auth`, server
clock, Admin SDK), already transactional, already two-phase, and already
idempotent via `operationId`. The event is added to its **write phase**, after
the replay guard returns — so it inherits every one of those properties rather
than re-implementing any of them.

## Architecture Alternatives Rejected

| Option | Rejected because |
|---|---|
| A — bounded array on the study item | Unbounded-ish document growth (§49), and no way to run one ordered, limited query across topics. |
| C — subcollection under each study item | A topic trail spans several questions, so it would need one query per question — an N+1 (§42). |
| D — enhance an existing attempt record | No such record exists. |
| E — a separate function/event writer | Would break atomicity with the counter update and add a second retry surface. |

## Event Contract

```
users/{uid}/studyEvents/{eventId}
  questionId     string
  outcome        "solved" | "struggled" | "again"   (canonical enum, untranslated)
  occurredAt     number   (server clock)
  sourceClassId  string | null                       (server-written)
  schemaVersion  1
```

**No question content** — not even subject/topic. `StudyItemRecord` documents
that rule for itself ("snapshotting here would leak private/class material into
a document the owner can read forever"), and an event outlives an item, so it
applies with more force. Subject/topic are joined on the client from the shared
question-metadata cache the Study Hub and feed already load — zero extra reads.

## Idempotency

Event id = the client's `operationId` when present (every current client sends
one), else `questionId__now`. `now` is captured once *before* the transaction
opens, so a Firestore transaction retry re-derives the same id and `set`
overwrites instead of appending.

A *callable* auto-retry without an operationId would mint a new event — but it
would equally re-increment the Phase 41 counters, because those rely on the
same guard. **The event is never weaker than the counters it accompanies**,
which is exactly the property that keeps the two consistent.

## Atomicity

One `runTransaction`. Counter update and event creation commit together; there
is no window where a counter moved but the event is missing, or vice versa.

## Timestamp Authority

Server only. `recordStudyOutcome`'s existing note applies verbatim — a client
cannot backdate an outcome to manufacture a recovery narrative.

## Legacy / Migration

**No backfill. No synthetic history. No bulk conversion.** Existing documents
are untouched and keep working. Pre-Phase-59 outcomes simply have no events —
which is the honest state, not a defect.

**Student D**: verified in the emulator to have `events=0` and one genuinely
counter-less legacy item. No trail, no zeros, no "no struggles" claim.

## Coverage Honesty

The two systems coexist and neither is presented as the other. A card shows a
trail **or** Phase 56's evidence bar, never both — the bar exists precisely
because a composition cannot be misread as a sequence, so pairing it with a
real sequence would confuse the two.

Observed live: Student A's card reads "Bu konuda 8 kez zorlandın" (cumulative,
Phase 41) above a 4-step trail (chronological, Phase 59). The cumulative figure
is larger than the trail, and nothing claims the trail is the whole history.

**No weekly claims** were built (§32/§33): a rollout-era timeline cannot prove
it covers a full week, so no time-window summary exists to overstate.

## Student Learning Trail

`İlerleme Hikâyem` → each topic moment. Oldest → newest, left to right, capped
at 4 steps, requiring at least 2 real events before rendering as a sequence
(one outcome is not a journey).

Shapes are display-only context, never a reclassification — Phase 42 remains
authoritative. `recovery` requires the sequence to *end* on a solve after a real
struggle; the same multiset in the opposite order is explicitly not a recovery,
and a test asserts that.

## Teacher Learning Trail

**Not implemented this phase**, with a valid architectural reason rather than an
omission: the read path and rules are complete and tested
(`getRecentClassLearningEvents` + the class-scoped rules grant + the composite
index), but wiring it into Student Performance was left out to keep this phase's
runtime surface to what was actually verified end-to-end. No teacher screen
queries events, so there is **no N+1 and no new teacher read**.

## Learning Story Fallback

A trail failure is non-fatal: `useLearningTrail` swallows the error, `events`
stays empty, and every card falls back to Phase 56's evidence bar. A timeline
error can never take down a screen whose cumulative story is still valid.

## Security

Student reads only their own events. Teacher reads only events whose
server-written `sourceClassId` names a class they own, for a real student member
of it — never a student's private/public history, never another class.

## Firestore Rules

`allow write: if false` — no create, update or delete from any client path, so
recorded outcomes are immutable and undeletable. 15 new rules tests cover owner
read/list, cross-student denial, unauthenticated denial, forge/rewrite/backdate/
delete denial, authorized teacher read + list, non-class-sourced denial,
wrong-teacher denial, non-member denial, and teacher write denial.

## Query Cost

Student story: **one** bounded query (`orderBy occurredAt desc, limit 40`).
Teacher: none (see above). No listeners, no polling.

## Write Cost

**+1 Firestore document write per confirmed learning outcome**, inside the
existing transaction. Stated plainly rather than disguised: an outcome now
writes 4 documents (item, summary, day, event) instead of 3.

## Indexes

One added to `firestore.indexes.json`: `studyEvents` (`sourceClassId` ASC,
`occurredAt` DESC), for the teacher-scoped query the rules require to be
provable. The student query needs no composite index (single-field order).

## Accessibility

Each step carries a numbered label ("1. Zorlandım") so chronology survives for
a screen reader that cannot see the chevrons. Outcome is carried by icon **and**
text, never colour alone. The row wraps rather than scrolls, so larger text
reflows instead of clipping.
