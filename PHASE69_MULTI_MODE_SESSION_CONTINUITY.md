## Phase 68 Single-Envelope Limitation

Phases 67/68 persisted **one envelope** under one AsyncStorage key
(`netflowedu.study.active-session.v1`), scoped by `userId` **and** `mode`. Both
`useReviewSession` and `useAdaptiveStudySession` wrote that key **whole**, so
one mode's session was the only session the device could hold.

## Exact Destructive Seam

Traced through the real functions and confirmed by a proof test written
**before** any fix. The overwrite does **not** happen where it might be
assumed:

| Moment | Destroys the other mode? |
|---|---|
| Entering the other mode (mount) | **No** — a mount only reads |
| `resolveSessionStart` mismatching on mode | **No** — it returns a new session and writes nothing |
| **First confirmed outcome in the other mode** | **Yes** — `saveActiveStudySession` replaced the whole key |
| **Completion stamp in the other mode** | **Yes** — same write path |
| **Acknowledging the other mode's completion** | **Yes** — `clearActiveStudySession` called `removeItem` on the shared key |

So the realistic sequence was:

```
adaptive 1/4  →  open Review  →  answer ONE review card
              →  adaptive session gone: no id, no receipts, no frozen plan
              →  returning to Adaptive silently starts a brand new session
```

Reproduced against `resolveSessionStart` / `buildActiveStudySession` /
`serializeActiveStudySession` directly: after the review write,
`resolveSessionStart({mode: "adaptive"})` returned `resumed: false`,
`receipts: []`, `plannedQuestionIds: []`, and a different session id. The
acknowledge path was worse — it removed the key outright.

## Product Goal

Mode switch is not session abandonment. Switching Review ↔ Adaptive must leave
the source session exactly as it was: same session id, same receipts, same
frozen adaptive plan, not completed, not acknowledged, not abandoned.

## Store Architecture

`src/features/study/services/studySessionStore.ts` — a pure, bounded container:

```
{ version: 3, slots: { mandatory?: Session, adaptive?: Session } }
```

Operations: `parseStudySessionStore`, `serializeStudySessionStore`,
`readStudySessionSlot`, `putStudySessionSlot`, `removeStudySessionSlot`,
`isStudySessionStoreEmpty`. All pure, all total, none throwing.

`resolveSessionStart` and `resolveCompletedSession` keep their existing
signatures and now read **this mode's slot** from the store. The sibling is
never consulted, never compared against, never touched.

## Slot Model

At most one slot per mode; each may be **absent**, **active**
(`completedAt: null`) or **completed** (stamped). Each slot keeps its own
`sessionInstanceId`, `startedAt`, `receipts`, `plannedQuestionIds` and
`completedAt`. Review can never reuse Adaptive's id and vice versa — they are
different slots created by different mounts.

## Schema Version

Writes are **version 3**. Reads accept **3**, and **1/2** through the legacy
parser. `ACTIVE_STUDY_SESSION_VERSION` remains 2 and now names the newest
*legacy* version this build can read. The storage **key is unchanged** — a new
key would have orphaned every session already in progress on a device, and the
payload's own version carries the migration instead.

A Phase 67/68 build reading a v3 record fails closed (its parser pins
`version !== 1` / `!== 2`), which is the correct direction: an older build must
never reinterpret this shape.

## V1/V2 Migration

Pure parser normalisation, no migration framework. A valid v1 or v2
single-session record is filed into the slot for the mode it already declared,
with its receipts, frozen plan and completion stamp intact, and the next save
writes v3. The legacy parser is **reused**, not re-implemented, so the two
formats cannot drift. Malformed legacy input yields an empty store — no heroic
recovery, and above all no timestamp reconstruction.

## Review Slot

Session id, receipts and completion state survive the entire adaptive
lifecycle (start, outcome, completion, acknowledgement) and an app reload.
Review still re-queries canonical due items on mount; **no queue snapshot and
no Firestore cursor are persisted**.

## Adaptive Slot

Session id, frozen `plannedQuestionIds` and confirmed entries survive the
entire review lifecycle and a reload. Phase 68's frozen-plan semantics are
unchanged: the plan is **never** regenerated by a mode switch, and new Phase
45/61/65 evidence still affects the **next** session.

## Slot-Preserving Updates

Enforced by the storage API, not by hook discipline (§18). `saveStudySessionSlot`
and `clearStudySessionSlot` take the mode explicitly, **re-read storage inside
the write**, replace only that slot, and carry the sibling through **by
reference** — so there is no field list to keep in sync and no way for a future
field to be silently dropped from the mode that was not being written.

Writes are serialised through a promise chain, because two hooks are mounted at
once on the study screen and two read-modify-writes interleaving at their
awaits could otherwise restore a stale sibling. The chain holds no session data
— it is a queue, not a cache, so nothing there can leak between users.

## Safe Handoff

Switching modes performs **no** write to the source slot: no completion stamp,
no cleared receipts, no acknowledgement, no regenerated plan, no "abandoned"
marker. Entering a mode only ever reads.

## Completion Coexistence

All four combinations are supported and tested: both active, completed review
beside active adaptive, active review beside completed adaptive, and **both
completed** — reachable precisely because completing one mode no longer touches
the other, and acknowledgement is a separate explicit act. Still bounded at two
slots; there is no shape in which a third can exist.

## Acknowledgement Semantics

Acknowledging clears **only** that mode's slot. The record is removed entirely
only when no mode holds a session, so nothing is left as an empty shell.

## Frozen Adaptive Plan Safety

Asserted directly: the frozen ids survive review creation, a review receipt,
review completion, review acknowledgement and an app remount, and are still the
plan the session started with even when the live plan has moved on completely.

## Review Pagination Safety

Untouched. No cursor is persisted, `mergeResolvedPages`, `interleaveReviewEntries`
and `trailingTopicKey` are not modified, and Phase 63/64 remain authoritative.

## User Isolation

Every slot carries its own `userId` and is matched exactly on hydration.
Student B receives none of Student A's evidence in either mode, and — following
Phase 67's own policy — A's slot is **left in place** rather than deleted,
because deleting it would destroy the real session of whoever it belongs to.
Storage stays bounded: one slot per mode, whoever owns it.

## Mode Isolation

A review envelope never hydrates as adaptive and vice versa. A slot whose own
`mode` contradicts the key it sits under is **rejected**, not repaired — that
guess would move a session's evidence between modes. Unknown mode keys are
never read at all, because the parser iterates the closed mode list rather than
the stored object's own keys.

## Technical Staleness

The 12-hour bound is retained and applied **per slot**, at read time only. A
stale slot is simply not resumed; it never deletes its sibling, and nothing is
deleted on read at all. Staleness still gates local *resume* and never decides
which outcomes belonged to a session — membership was fixed when each outcome
was confirmed.

## Storage Failure Behavior

Read failure returns null and the session starts fresh in memory; study
continues, and nothing is reconstructed from the backend. Write failure returns
`false`, the in-memory session continues, the server outcome stands, and the
sibling slot is never cleared as a side effect. No server rollback exists or is
attempted.

## Multi-Tab Limitation

`localStorage` is not transactional. The write queue serialises mutations
**within one app instance**; two browser tabs open on the app remain
last-write-wins for the whole record. No BroadcastChannel or distributed mutex
was built — that would be a large mechanism for a case the product does not
require, and the honest answer is to state the bound rather than imply
atomicity.

## Local Storage Cost

One key. **Reads:** one per session mount (unchanged), plus one inside each
mutation for the merge. **Writes:** one per confirmed outcome (unchanged), one

## Known Limitations

- **Multi-tab is last-write-wins.** The write queue is per app instance; two
  browser tabs can still clobber the record. Stated rather than papered over.
- **Two accounts share one key.** Slots are scoped by `userId` and never
  hydrate for the wrong account, but a slot for one mode is replaced by
  whichever user writes that mode next. Bounded at two slots total; this is not
  multi-account persistence and was not turned into it.
- **Assignment remains excluded** — its completion boundary is
  assignment-lifetime, not session-bound, so a session summary would
  under-report against the claim above it (Phase 68's reasoning, unchanged).
- **Immersive Feed remains open-ended** — no slot, no closure, deliberately.
- The 12-hour staleness bound still means a session abandoned for longer is not
  resumed; per slot, and only ever under-counting.
